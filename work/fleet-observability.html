Case study

Fleet observability (Prometheus + Grafana)

PrometheusGrafanaAlertmanagerMikroTik exportersSlackAnsible

Scale ~50 RouterOS devices scraped · hypervisor and backup hosts alongside · dashboards and Slack alerts deployed from one Ansible repo

Situation

Campus already had a traditional NMS. Router and hypervisor visibility for the ops day-to-day was thin: CPU/WAN pain showed up as tickets, not graphs. Alerts were uneven (some Slack paths dead, some media types disabled).

Task

Stand up a Prometheus/Grafana stack for the MikroTik fleet and related hosts, with actionable Slack alerts and an idempotent Ansible deploy path.

Approach

  1. Stable scrape keys — router metrics keyed by mgmt IP so renaming RouterOS identity does not break history.
  2. Explicit add-router workflow — pass IPs; do not pretend inventory auto-discovery is safe.
  3. Alert path end-to-end — Alertmanager → Slack templates; verify with a controlled fire, not “config looks fine.”
  4. Dashboards by role — fleet overview, DHCP churn approximations, WireGuard peer health where enabled.
  5. Document cross-repo risks — monitoring playbooks assume sibling checkouts and vaulted secrets.

Result

  • Fleet dashboards and Slack alerts for down jobs / storage / backup signals.
  • Operators can see per-router load and lease churn without WinBox hopping.
  • Playbooks are re-runnable; secrets stay in vault, not Git.

Interview soundbites

“Identity rename must not invalidate Prometheus history — key on the scrape address.”
“I don’t trust an alert until I’ve forced it once.”
