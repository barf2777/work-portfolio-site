Case study

Documentation as an operations system

worklogsrunbookschangelogtroubleshooting pattern libraryagent-assisted discipline

Scale ~120 markdown documents · 18 operator runbooks · daily worklogs with weekly rollups · reusable troubleshooting notes kept separate from the timeline

Situation

Single-operator / small-team IT on a complex brownfield campus. Knowledge lived in chat, WinBox, and memory. Handoffs and resume-after-interrupt were expensive.

Task

Build a documentation system that (1) captures what I did today, (2) records what changed in infra, and (3) extracts reusable fixes — without turning every day into a novel.

Approach

  1. Three layers — daily worklog (granular timeline), changelog (infra state), runbooks/architecture (how to operate).
  2. Weekly rollups — theme bullets with time ranges; highlights/risks for Monday review.
  3. Close-thread outcomes — when something finishes, one past-tense bullet with blast radius / done vs deferred.
  4. Troubleshooting notes — symptom → cause → fix → prevent, newest first; only when the symptom was misleading and the fix is repeatable.
  5. Agent rules — logging during live troubleshooting is mandatory; live mutations still need per-change human approval.
  6. Portfolio mining — weekly “portfolio candidates” (internal) → separate sanitized public rewrite (this repo). Never auto-copy.

Result

  • Resume a multi-week thread from the log instead of from memory.
  • Hiring-facing case studies exist because the private archive is dense enough to rewrite.
  • New operators (or future you) get jump-table runbooks and a controlled vocabulary instead of synonym soup.
