Backup visibility and scrape pitfalls

PBSfile backupnode_exporterfirewalldcronAnsible defaults

Scale multi-terabyte backup estate (hypervisor guests via Backup Server plus file-level clients) · two backup products with different failure modes · daily digest to chat

Situation

Backups existed (hypervisor snapshots / PBS, file-level backup appliances) but operators lacked a single daily signal: is the pool healthy, is free space OK, did last night fail? Host agents “listening” locally still looked down from Prometheus.

Task

Expose backup hosts to the metrics stack, alert on failure and storage pressure, and leave a daily digest ops can skim in Slack.

Approach

  1. Exporter + node metrics on PBS and backup appliances via Ansible; keep Synology-class hosts on a digest path when native exporters are awkward.
  2. Verify scrape from the collector — curl on localhost is not enough; host firewalld often allows app ports but not :9100 from the monitoring subnet.
  3. SSH key hygiene — OpenSSH .pub must be one line; RFC4716 multi-line pubs make ssh-copy-id write garbage into authorized_keys.
  4. Cron env discipline — scripts that need webhook URLs must load the env file themselves (or use export); shell . env without export silently drops vars for child processes.
  5. Standalone playbook defaults — roles used outside site.yml need defaults/ so required vars are not “undefined.”

Result

  • Backup storage and failure signals land in Slack; Grafana covers host disk and exporter health.
  • Troubleshooting notes capture the “active but unreachable” pattern for the next host.
  • PBS datastore recovery documented when a pool was unimported / over-complicated with a file vdev.
